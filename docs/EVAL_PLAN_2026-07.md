# 多模型協作評測計畫（#22 / P3-20）

> **第二版，2026-10-28 重做。** 第一版（2026-07）是一份「跑完記下來」的清單，不是實驗：
> 分組同時改變了好幾件事、每題只跑一次、而且由作者自己評分。那樣的結果無論多漂亮都說服不了人。
> 這一版把它改成**一個因子、可重複、可盲評、事前登錄**的對照實驗，並且把能機器判定的部分
> 交給 `tools/EvalScorer` 去算，不靠自律。
>
> 要回答的問題只有一個：**多模型編排是否優於單一模型？** 以及它值不值多花的錢與時間。

## 一、設計

> **2026-10-29 更正（第一階段九次先導執行後）**：下表原本把 A／B 稱為「單一模型」，那是錯的。
> 逐筆帳目顯示三組都是多模型流程：意圖判斷（GPT）與搜尋研究（Perplexity Agent API +
> `openai/gpt-5.6-sol`）在三組完全相同，**唯一的差別是由哪個模型寫最終答案**。
> 選了 Claude 的 B 組，九成以上的花費其實是 OpenAI。詳見 `docs/eval/runs/2026-10-29/RESULTS.md`。
>
> 因此第一階段能回答的只是「最終答題模型的選擇是否影響正確率與成本」。
>
> **同日更正**：手動模式的每一步現在都先用所選模型（意圖判斷、配圖判斷、搜尋研究、記憶萃取、
> 文件撰寫）；所選模型確定失敗時會改用其他模型，並在答案最上方告知。
> 所以手動組在**沒有發生替補**時就是真正的單一模型組，原本的問題可以直接回答。
> 有沒有發生替補不靠人看：`ingest` 會逐次檢查並寫進 `metrics.csv` 的 `single_model` 欄，
> 標為 `no` 的手動執行要排除或另外分析。
> 第一階段的九次是在修改前的版本上跑的，不能與之後的執行合併。

**一個被操作的因子**：由哪個模型寫最終答案（前段的意圖判斷與搜尋研究，三組相同）。

| 組 | App 設定 | 實際差別 |
|---|---|---|
| **A** | 手動模式，固定 **GPT-5.6 Sol** | 最終答案由 GPT 寫 |
| **B** | 手動模式，固定 **Claude Sonnet 5.5**（第一階段用的是 Sonnet 5） | 最終答案由 Claude 寫 |
| **D** | **API Auto**（自動選模型） | 由系統挑選最終答題模型（第一階段三次都選了 pplx-sonar） |

模型名稱以 App 當下的選單為準，並由 `ingest` 從存檔記錄實際用到的模型；
不要再依手冊上寫的名字判斷——第一階段的手冊就寫錯了（沿用了七月版的 GPT-5.5／Sonnet 4.6）。

> 組別刻意跳過 C，留給下節那個目前做不到的對照組，避免日後編號混亂。

**保持固定**：題目原文（逐字相同）、同一天內跑完同一題、交付格式一律開「產生」、
固定素材（T06／T09）三組貼同一份檔案、每日花費上限、網路環境。

**判準（事前定好，不准事後改）**：
多模型要算贏，必須贏過**兩個單模型組中較好的那一個**，而不是贏過它們的平均。
理由：使用者的替代方案是「挑一個好模型用」，不是「隨機挑一個模型用」。

### 本實驗分不出來的那一件事（必須寫在結論裡）

Auto 組同時做了兩件事：**挑模型**與**多代理編排**。本系統的設計上這兩者綁在一起
（`AgentRuntime` 只有在 `IsAutoModelSelectionEnabled()` 為真時才走進階編排），
所以「多模型編排的效果」裡含有「挑到更適合的模型」的效果，無法分離。

要分離需要一個目前不存在的設定：**鎖定單一模型但保留多代理編排**。
程式裡已有 `NodeExecutionDecision.ForceSingleModel`（委派子代理用），
把它接到一個評測專用開關即可構成完整的 2×2，那是後續工作，不在本次範圍。
**在那個開關做出來之前，本實驗的結論只能說「本產品的 Auto 模式 vs 單一模型」，
不能說「多代理架構本身優於單模型」。**

```
docs/eval/materials/T06_abstract_en.txt  T06 的固定英文摘要（本評測自撰）
docs/eval/materials/T09_article_zh.txt   T09 的固定中文文章（本評測自撰）
```

| # | 類型 | 必要項 | 其中必備 |
|---|---|---|---|

| T02 | 研究→分析（美國利率對台灣科技股） | 6 | 5 |

| T07 | 簡報（AI 資料隱私風險，6 頁） | 6 | 3 |
| T08 | 表格（近五年電動機車銷量，Excel） | 5 | 4 |

清單格式與撰寫規則見 [docs/eval/README.md](eval/README.md)。三條最重要的規則：

1. **每一條都必須只從題目本身推得出來**，不准看了某次產出再回頭補——那叫改考卷。
2. **清單在開跑前 commit，並把 commit hash 抄進紀錄表**。這是整份實驗可信度的關鍵：
   事後任何人都能確認清單不是為了好看而調整過的。
3. **機器量的是「必要主題有沒有出現」，不是「說得對不對」。** 事實正確率一律由人評。

### 重複次數（成本與資訊量的取捨）

| 範圍 | 題目 | 組別 | 重複 | 次數 |
|---|---|---|---|---|
| 主實驗 | T01、T02、T03、T10 | A／B／D | 3 | 36 |
| 次實驗 | T04～T09 | A／B／D | 1 | 18 |
| | | | **合計** | **54** |

主實驗挑這四題，因為它們最可能分得出差異（兩題重研究、一題重研究後的交付、一題測幻覺）。
重複只放在主實驗，是因為重複的用途是**估組內變異**——只要有一部分題目有重複，
就能判斷其餘題目的組間差距是否大於同組重跑的波動。

**成本**：先跑完 T01 的 9 次（A/B/D × 3），把決策窗的實際金額抄下來，再乘以 6 外推，
不要用猜的數字編預算。開跑前把每日上限調高到足以跑完當天的份量，免得中途被擋導致作廢。

## 三、執行與紀錄

一次 run 一個資料夾：

```
docs/eval/runs/2026-11-02/
  outputs/T01-A-1.txt      ← 產出全文，檔名＝題號-組別-第幾次
  outputs/T01-A-2.txt
  …
  metrics.csv              ← 從決策窗抄下的客觀欄
  notes.md                 ← 當天的環境與異常（哪一次重試過、哪一次被上限擋到）
```

`metrics.csv` 的欄位（第一列照抄）：

```
task,group,rep,tokens,cost_usd,cost_twd,seconds,models
```

**這張表不用手抄。** `outputs/` 與 `metrics.csv` 都由 `ingest` 從 App 的專案存檔產生：

```bash
dotnet run --project tools/EvalScorer -- ingest --run docs/eval/runs/<日期> --project "<專案存檔.json>"
```

存檔裡本來就逐筆記了每次執行的實際 token、USD、耗時、選模型方式與實際模型，
所以三件事變成不可能做錯：成本是逐筆金額的加總而非顯示字串、
組別由存檔推定而非操作者填寫、第幾次依實際執行時間排序（同一存檔重跑結果相同）。
操作者唯一要做對的事是**把組別的開關設對**。

`models` 欄會列出該次實際用到的所有模型——D 組的模型鏈是結論裡最有說服力的一手材料。

### 要跑之前的兩道檢查

```bash
dotnet run --project tools/EvalScorer -- validate
dotnet run --project tools/EvalScorer -- freeze --run docs/eval/runs/<日期>
```

`validate` 檢查十份清單是否合法、有沒有題目已過有效期限、有沒有題目缺少必備項
（缺必備項的題目永遠不會不及格，等於沒有驗收條件）。

`freeze` 把十份清單與兩份固定素材的 SHA-256 寫成 `preregistration.txt`。
整份實驗的可信度取決於「清單是跑之前就定好的」，而口頭保證沒有用；
雜湊讓任何人事後都能重算驗證。用檔案內容的雜湊而不是只記 git commit，
是因為未提交的修改不會反映在 commit hash 上——那個漏洞正好是這份登錄要堵的。

### 分階段執行（先量單價，再決定要不要跑完）

不要一開始就跑 54 次。第一階段只跑 **T01 的九次**（A／B／D × 3），
用實際金額取代預算裡的猜測值，再決定其餘 45 次要不要跑。
第一階段的逐步操作見 `docs/eval/runs/2026-10-29/RUNBOOK.md`。

## 四、計分

### 4.1 機器判定（不需要人，也不會花錢）

```bash
dotnet run --project tools/EvalScorer -- score --run docs/eval/runs/2026-11-02
```

輸出 `scores.csv` 與分組摘要，三個指標：

| 指標 | 定義 |
|---|---|
| **字樣命中率** | 命中的必要項 ÷ 必要項總數 |
| **必備項齊備率** | 必備項全中、且未踩到禁止內容的比例 |
| **禁止內容命中率** | 踩到幻覺／保證式說法等反面條件的比例 |

兩者刻意分開：命中率 100% 仍可能必備項不齊（例如 T04 把該講的都講了，
卻多寫一句「保證獲利」）。只看平均分會看不見這種失敗。

**名稱很重要。** 這三個數字量的是「必要字樣有沒有出現」，不是「說得對不對」，
也不是「任務有沒有完成」。第四輪審查用一行「排隊、變異、批量、瓶頸、量測。」
命中了摘要題的五個重點，證明舊名稱（內容涵蓋率、及格率）解釋過強。
清單已改用 at_least 要求數個相關字樣共同出現、並把篇幅下限列為必備項，
同一行字現在命中 0/7；但字樣比對終究不是內容判讀，引用這些數字時必須連這句話一起引用。

### 4.2 盲評（人）

```bash
dotnet run --project tools/EvalScorer -- blind --run docs/eval/runs/2026-11-02
```

產生 `blind/S1000.txt…`、`blind/rating_sheet.csv`（只有代號）與 `blind/key.csv`（對照表）。
作法：

1. 把 `blind/` 裡的 `S####.txt` 與 `rating_sheet.csv` 交給**兩位非作者**評分者。
2. `key.csv` 在所有評分收齊之前不要打開，也不要給評分者。
3. 四個維度各 1～5 分，錨點如下。

| 維度 | 5 分 | 1 分 |
|---|---|---|
| 事實正確 | 題目規格 `human_checks` 列的每一項都查得到支持 | 有明顯錯誤或憑空捏造 |
| 來源可查 | 關鍵主張都有打得開、且頁面真的含該主張的連結 | 完全沒有來源 |
| 指令遵守 | 格式／字數／語氣全照要求 | 偏題 |
| 交付品質 | 可直接交出去用 | 要大改 |

4. **事實正確率**另外單獨算：逐項判定 `human_checks` 為「支持／不支持／無法判定」，
   正確率 = 支持 ÷（支持＋不支持）。「無法判定」要記下來，它本身就是結論的一部分
   ——連人都查不到的來源，不該算系統查到了。
5. 記錄**兩位評分者的一致率**。不一致的項目不要平均掉，列出來；差異大的維度在結論裡要說。

## 五、分析

每一格（題目 × 組別）有 3 次或 1 次。有重複的格子取**中位數**與**全距**。

**判準**（事前定好）：
> 某指標上，D 組中位數減去「A、B 中較高者」的中位數，**大於兩組全距的上限**，
> 才稱為「可辨差異」；否則記為「在本樣本量下無法區分」。

n=3 不做顯著性檢定。寫「無法區分」比寫一個沒有檢定力的 p 值誠實，也更容易被接受。

**成本效率**：每提高一個百分點的必要內容涵蓋率，D 組比較好的單模型組多花多少錢與多少秒。
這比「貴了幾倍」有用——使用者要決定的是值不值得，不是貴不貴。

**事前登錄的預測**（開跑前填好，跑完不准改，對錯都寫進結論）：

| 題型 | 預測 | 若預測錯了代表什麼 |
|---|---|---|
| 研究類（T01～T03） | D 組在「來源可查」與事實正確率上可辨地贏 | 多模型編排在本系統沒帶來查證優勢，要檢查搜尋結果到底有沒有進最終提示 |
| 陷阱題（T10） | D 組踩到禁止內容的比例較低 | 編排沒有降低幻覺，「可稽查」的宣稱要改口徑 |
| 寫作／翻譯（T05、T06） | 三組難以區分 | 若 D 組明顯較好，表示編排在非研究類也有價值，值得重新評估分流策略 |
| 全部 | D 組成本與耗時明顯較高 | 若沒有，代表成本優化比預期有效，是好消息，但要確認不是因為跑了簡化路徑 |

**結論寫成一句話**：
> 「在 ＿＿ 類任務上，本產品的 Auto 模式以 ＿＿% 的額外成本與 ＿＿% 的額外耗時，
> 換得必要內容涵蓋率 ＿＿ 個百分點、事實正確率 ＿＿ 個百分點的變化；
> 在 ＿＿ 類任務上與單一模型無法區分。」

這句話的用途：給學長的答覆、簡報的數據頁、研究所備審的實驗段落。
**包括「無法區分」那一半也要寫出來**——那是分流省錢的依據，也是這份實驗沒有作弊的證據。

## 六、注意事項

- 跑之前把每日花費上限調到足夠，免得中途被擋；被擋的那一次要作廢重跑，並記在 `notes.md`。
- 同一題三組同一天跑完。即時資料類跨日就不公平了。
- 全程截圖決策窗，尤其 D 組的多模型軌跡與成本明細。
- 中途強制停止的那一次一律作廢——部分產出算不出涵蓋率，留著只會汙染平均。
- `docs/eval/runs/_example_smoke/` 是計分器的煙霧測試假資料，**不是結果**，別混進分析。

## 七、完成後要補的三件事

1. 把 `scores.csv`、盲評表與一致率存進同一個 run 資料夾，連同 commit hash。
2. 更新專題報告「研究限制」一節：把「尚待獨立評估」改成實際的評估結果，不論結果好壞。
3. 若結論是「某類任務單模型就夠」，把它接回產品：讓系統在那類任務自動降級省錢，
   並在報告裡說明這個決策的依據來自本實驗。
