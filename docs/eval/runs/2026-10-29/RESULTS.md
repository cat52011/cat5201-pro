# 第一階段結果：T01 九次（2026-10-29）

> **一句話結論**：這九次是一次**先導執行（pilot）**，不是實驗結果。
> 它沒有回答「多模型是否優於單一模型」——因為它揭露了實驗設計本身的錯誤：
> 三組其實都是多模型流程，唯一的差別是「誰寫最終答案」。
> 但它找到了四個真實的缺陷，其中兩個是先前的程式碼審查與單元測試都沒抓到的。

事前登錄：`preregistration.txt`（題目規格與素材的 SHA-256，開跑前凍結）。
原始資料：`metrics.csv`（由 `ingest` 從專案存檔逐筆加總，非人工抄寫）、`scores.csv`、`outputs/`。

## 一、實際跑了什麼

| 組 | 手冊寫的 | 實際用的 | 每次呼叫鏈（逐筆帳目） |
|---|---|---|---|
| A | GPT-5.5 | **GPT-5.6 Sol**（手動） | 意圖判斷 GPT → 搜尋研究 ×2–3 → **主回覆 GPT** |
| B | Claude Sonnet 4.6 | **Claude Sonnet 5**（手動） | 意圖判斷 GPT → 搜尋研究 ×2–3 → **主回覆 Claude** |
| D | API Auto | **API Auto** → 自動選中 Perplexity Sonar | 模型選擇 GPT → 意圖判斷 GPT → 搜尋研究 ×2 → **主回覆 pplx-sonar** |

**手冊上的模型名稱是錯的**——那是從七月版計畫沿用下來的，App 的選單早已換成新世代。
`ingest` 讀的是存檔裡的實際模型，所以分組沒有因此弄錯，但手冊要改。

「搜尋研究」在三組都是同一個東西：Perplexity Agent API，實際執行模型為 `openai/gpt-5.6-sol`。

## 二、設計錯誤：三組都不是「單一模型」

實驗計畫把 A／B 稱為「單一模型組」，D 稱為「多模型編排組」。逐筆帳目顯示這不成立：

- **A 組**：全程 OpenAI，但仍是四到五次呼叫的流程（意圖判斷、兩三次搜尋研究、主回覆）。
- **B 組**：使用者選了 Claude，但**九成以上的花費是 OpenAI**——
  以 B-1 為例，Claude 主回覆 US$0.0274，OpenAI 搜尋與意圖判斷合計 US$0.3235。
- **D 組**：比 A、B 多一次「模型自動選擇」，然後選中 pplx-sonar 來寫最終答案。

所以三組的真正差別只有一個：**最後是誰把研究結果寫成答案**。
這其實是一個控制得不錯的比較——前段流程完全相同——但它回答的是
「最終答題模型的選擇是否重要」，不是「多模型是否優於單一模型」。

先前的計畫書曾寫「能力層對手動與 Auto 一視同仁，所以搜尋不是因子」，這句話是對的；
但從它推出「A／B 是單一模型」是錯的——能力層本身就呼叫了別的模型。
**原計畫要回答的那個問題，在目前的系統上根本沒有可以對照的「單一模型」組。**
要做出真正的單一模型組，得有一個「關閉能力層、只用一個模型直接回答」的評測開關。

## 三、客觀指標（依事前登錄的判準）

| 組 | n | 成本中位數 | 成本全距 | 耗時中位數 | 耗時全距 | 字樣命中率 | 必備項齊備 |
|---|---|---|---|---|---|---|---|
| A | 3 | US$0.304 | 0.128 | 71.8 s | 28.1 s | 95.2% | 2/3 |
| B | 3 | US$0.267 | 0.088 | 62.3 s | 14.1 s | 100% | 3/3 |
| D | 3 | US$0.251 | 0.023 | 55.9 s | 11.9 s | 100% | 3/3 |

判準（開跑前寫定）：D 減去「A、B 中較好者」的差距，要大於組內全距才算可辨差異。

- **成本**：D 比 B 便宜 US$0.016，組內全距最大 0.128 → **無法區分**
- **耗時**：D 比 B 快 6.4 秒，組內全距最大 28.1 秒 → **無法區分**

D 組的全距明顯最小（成本 0.023、耗時 11.9 秒），三次都只做了兩次搜尋研究；
A、B 組的高點都來自做了三次搜尋研究的那一次。**成本的主要變異來源是搜尋研究的次數，不是組別。**
九次之中，搜尋研究佔單次成本的 74%–92%，主回覆只佔 7%–23%。

**實際單價**：每次 US$0.24–0.40（約 NT$7.6–12.7）。原計畫的預算數字是猜的，以此取代。

> **成本數字的更正（同日稍晚發現）**：上表的搜尋研究成本是用本機價目表 $5/$30 算的，
> 但 Perplexity 目前公布的價格是 $4/$20（≤272k 輸入）。更糟的是，那幾筆紀錄的備註寫著
> 「費用取自 API 回報」，實際上服務商回報的金額被讀進來之後就丟掉了，記下的仍是本機估算。
> 服務商回報的真實金額當時沒有存下來，無法事後還原；以 $4/$20 重估，搜尋研究成本約高估兩成五，
> 單次總成本約高估兩成。三組的搜尋階段完全相同，所以**組間比較不受影響，絕對金額偏高**。
> 這兩個問題都已修正：現在服務商有回報就用回報值。
以 T01 這種研究型題目估，剩餘 45 次約 US$11–18；但 T03／T07／T08 會產出檔案，單價會更高。

## 六、這次找到並已修正的缺陷

1. **決策視窗顯示了沒被呼叫的模型**（使用者回報）。
   關閉 Auto 後，「模型」欄仍顯示 Perplexity Sonar。原因是工作區推導產物模型時寫死了
   「搜尋固定由 Perplexity Sonar 執行」，但實際是 Perplexity Agent API + `openai/gpt-5.6-sol`，
   逐筆帳目裡 A／B 組一次 pplx-sonar 都沒有。現在由能力層自己回報實際模型，推導不出來就留空。

2. **「僅核對網域」警告橫幅一次都沒出現**（作者自己的錯）。
   前一輪新增了這個橫幅與給模型的硬規則，測試也全過；但呼叫端只在「沒拿到資料」時才去取橫幅，
   而「拿到了但只核對網域」算有資料，於是整段被無聲跳過。這跟第四輪審查指出的缺陷是同一種
   ——新增了正確的狀態，卻讓舊的判斷決定要不要用它——只是發生在下一層。
   現在收斂成單一屬性 `NeedsUserNotice`，並把「只有搜尋摘錄」這個更弱的狀態也納入提示。

3. **小預算呼叫會對 Opus 5.5 送出非法設定**。
   `thinking:{type:"disabled"}` 在 Opus 5.5 上任何 effort 都回 400，而 Opus 已在九月升到 5.5。
   400 之後會被 fallback 默默換模型重跑。現在依型號給出各自合法的設定。

4. **Sonnet 5 → Sonnet 5.5**（同價）。比照先前 Opus 升級的方式：
   舊專案檔裡的 `claude-sonnet-5` 路由到新版，但歷史紀錄照實顯示 Sonnet 5——
   這九次就是用 Sonnet 5 跑的，紀錄不能被改寫。

## 七、下一步建議（依重要性）

1. **先修清單，不要急著跑剩下 45 次。** T01 的營收項改用 `number` 類型（數值＋別名＋容許誤差），
   否則正式實驗會重演這次的天花板效應——三份寫錯十倍的產出照樣滿分。
2. **決定實驗要問什麼。** ~~若要回答原本的問題，需要先做出評測開關~~——
   同日已依使用者指示改成：手動模式的每一步都先用所選模型；**所選模型確定失敗時可以改用其他模型，
   但一定在答案最上方告知**。文件撰寫者預設也是所選模型，使用者可在確認框親手改選。
   因此手動組在**沒有發生替補**時就是真正的單一模型組，原本的問題可以直接回答。
   `ingest` 會自動檢查每一次手動執行是否真的只有所選模型參與（`metrics.csv` 的 `single_model` 欄），
   有替補的那幾次要排除或另外標記。以此回頭檢查第一階段：**A 組三次都是單一模型**
   （全為 GPT-5.6 Sol，搜尋經 Perplexity 的服務），**B 組三次都不是**（選 Claude，意圖判斷與搜尋卻是 GPT）。
3. **用修正後的版本重新凍結、重新執行。** 這九次跑在警告橫幅失效的版本上，
   而且 Sonnet 已升級，結果不能與之後的執行合併計算。
4. **盲評照做。** `blind/` 已產生九份代號檔與空白評分表；`key.csv` 在評分收齊前不要打開。
