# 必要內容清單：格式與撰寫規則

這個資料夾把「什麼算是講到了」寫成機器讀得懂的形式。
在這之前，本專題有兩個問題一直答不出來：

- 簡報壓到使用者要的頁數時，**被刪掉的是不是重要的東西**？
- 一份產出**有沒有把該講的講到**？

兩個都答不出來的原因是同一個：「必要」從來沒有被寫下來過。
所以沒有「內容保留率」可言——不是量不準，是沒有定義。

```
docs/eval/
  README.md          ← 本檔：格式與規則
  tasks/T01…T10.json ← 十題的必要內容清單
  materials/         ← 固定素材（三組貼同一份）
  runs/<日期>/       ← 每次執行的產出、客觀欄與分數
```

程式端：[`cat5201.Core/EvalRubric.cs`](../../cat5201.Core/EvalRubric.cs)（比對器）、
[`tools/EvalScorer`](../../tools/EvalScorer)（命令列計分器）、
[`tests/cat5201.Tests/EvalRubricTests.cs`](../../tests/cat5201.Tests/EvalRubricTests.cs)（含「repo 裡這十份清單必須合法」的測試）。

## 一、這把尺量得到什麼、量不到什麼

**量得到**：必要字樣有沒有出現、關鍵數字有沒有被保留（含正負號）、有沒有附指定網域的連結、
有沒有明確表示「無法確認」、字數有沒有照要求、有沒有踩到禁止內容。

**量不到**：說得對不對，以及**這件事有沒有做完**。

所以這個數字叫**字樣命中率**，不叫「內容涵蓋率」，更不叫「內容保留率」。
2026-10-28 第四輪審查用一行字打穿了舊名稱：對「摘要五個重點」這一題，只送出

> 排隊、變異、批量、瓶頸、量測。

就命中了五個重點項，拿到 83.3%、判定及格。那不是一份摘要，只是列詞。

縮小這個差距的辦法有，但消除不了：
把每個重點改成 `at_least`（要求概念與後果等**兩個以上相關字樣共同出現**，
才算在陳述一個主張而非點名一個詞）、把字數下限列為必備項。
改完之後同一行字的命中率是 0/7。

但它終究是字樣比對。「營收 9,890 億元」命中必要項，不代表那個數字是真的——
只代表這份產出有在講營收，而且給了一個數量級合理的數字。
事實正確率一律由人依每題的 `human_checks` 逐項判定。

同理，`CriticalItemsSatisfied` 刻意不叫 `Passed`：
「及格」會被讀成「完成了任務」，而這裡只驗了字樣。它是必要條件，不是充分條件。

這條界線寫在程式註解、計分器輸出與本檔三處，是故意的：
一旦有人把字樣命中率當成正確率或完成度，整套評測就從「證據」變成「誤導」。

同理，`kind: source` 只驗**網域**。在真實的主管機關網域下編一個不存在的路徑
（例如 `https://www.sec.gov/not-a-real-document`）仍會通過，因為沒有人把那一頁抓下來讀過。
所以凡有 `source` 項的題目都**必須**列 `human_checks`，測試會強制這件事。

## 二、清單怎麼寫（三條規則）

1. **每一條只能從題目本身推得出來。**
   先跑一次、看產出寫了什麼、再回頭把清單改成剛好對得上——那是改考卷，不是評分。
2. **開跑前 commit，並把 commit hash 抄進該次 run 的 `notes.md`。**
   這是整份實驗可信度的來源：任何人都能確認清單沒有為了好看而事後調整。
3. **至少要有一個 `critical` 項。**
   沒有 `critical` 的題目永遠不會不及格，等於沒有驗收條件；`validate` 會警告，測試會失敗。

### critical 該給誰

給「缺了就等於沒完成這件事」的項目：結論、限制、必答的主題、陷阱題的拒答。
不要給「有比較好」的項目——那是涵蓋率在量的東西。

判斷方式：如果一份產出缺了這一項，你還願意把它交出去嗎？不願意，就是 critical。

另外建議每題都放一個 `length` 必備項當**篇幅下限**。
這不是在獎勵廢話，而是擋掉「只列關鍵詞就通過」這種退化答案——
一行字無論命中幾個字樣，都不可能是一份完成的交付物。

## 三、欄位

```jsonc
{
  "task_id": "T01",                  // 必填，全資料夾唯一
  "title": "即時研究：…",
  "category": "即時研究",
  "prompt": "研究台積電最近一季財報…",   // 題目原文，逐字照打；三組貼的就是這一段
  "expires_on": "2027-10-01",        // 選填：這天之後本題失效（答案可能已公開）
  "required": [ … ],                 // 必要內容清單，不可為空
  "forbidden": [ … ],                // 選填：不該出現的東西
  "human_checks": [ … ]              // 人工抽查項；有 source 項時必填
}
```

### required 的 kind

| kind | 判定 | 必填欄位 | 用在 |
|---|---|---|---|
| `any_of` | 任一樣式出現 | `patterns` | 最常用。同一件事的多種寫法 |
| `all_of` | 全部樣式都出現 | `patterns` | 「兩種做法都要談到」 |
| `at_least` | 至少命中 `min_count` 個**不同**樣式 | `patterns`、`min_count` | 「舉三個案例」「列五個年度」 |
| `number` | `aliases` 附近有落在誤差內的數字 | `number`、`aliases` | 保留原文數字、核對特定數值 |
| `source` | 出現指定網域下的連結 | `domains` | 「可信來源」 |
| `declines` | 明確表示無法確認／尚未公布 | （`patterns` 可補充） | 陷阱題 |
| `length` | 字數落在區間內 | `min_chars` 或 `max_chars` | 「300 字的信」 |

共同選填欄位：`critical`（缺了就不及格）、`label`（給人看的名稱，會出現在「缺了哪一項」裡）。

### 比對的鬆緊

- **正規化**：全形轉半形、轉小寫、刪掉所有空白。
  所以清單寫 `2026年第二季`，產出寫 `2026 年第二季`、`２０２６年第二季` 都算命中——
  這種差異跟內容有沒有講到無關。
- **不做詞幹或同義詞推論**。`毛利率` 不會被 `毛利` 命中。
  要涵蓋多種寫法就把它們列進 `patterns`，不要靠比對器猜。
- **`number` 要求數字出現在別名附近**（±120 字元）。
  否則「文章裡剛好有個 989」會被算成「營收 989 億」。
  支援量詞：`萬 億 兆 千 k m mn b bn million billion thousand`，以及 `1,234.5` 這種千分位。
  `tolerance_percent` 預設 1%；要求完全相等就寫 0。
- **`number` 認正負號**（`-`、`−`、全形減號、中文「負」）。
  這是第四輪審查抓到的洞：原本「EPS 必須是 5」會被「EPS: -5」判成命中，
  因為樣式只抽出了 `5`。一個會接受符號相反數字的計分器，分數不能用來支持任何品質主張。
  兩個殘留限制：負號只在前一個字元不是數字時才算符號（否則 `2024-05` 會被讀成 −5），
  因此 `2024-05` 裡的 `05` 仍可能被當成 5——這也是 `number` 一律要求給別名的原因；
  另外「虧損」「下跌」這種**語意上的負**不算負號，要求負值請在清單裡直接寫負數。
- **`source` 比對到網域邊界**，不是字串包含。
  `sec.gov` 會命中 `www.sec.gov`，但不會命中 `sec.gov.evil.example` 或 `notsec.gov`。
- **`length` 計字不含空白**，中英文都算一個字元。這不是嚴格的「字數」定義，
  但三組用同一把尺，比較才公平。

### forbidden

```jsonc
"forbidden": [
  { "id": "F1", "label": "編造得主或獲獎理由",
    "patterns": ["得主是", "獲獎者為", "因其在"] }
]
```

踩到任何一條就**直接不及格**，不管涵蓋率多高。

樣式要窄。`patterns` 是字面子字串，不是正規表示式——寫 `由.*獲得` 永遠不會命中。
寬樣式造成的誤判比漏抓更糟：它會把一份好產出判成幻覺。

## 四、怎麼用

```bash
# ① 開跑前：檢查清單合法、沒過期、每題都有驗收條件
dotnet run --project tools/EvalScorer -- validate

# ② 開跑前：把清單的內容雜湊凍結成事前登錄
dotnet run --project tools/EvalScorer -- freeze --run docs/eval/runs/2026-10-29

# ③ 跑完後：從 App 的專案存檔讀出產出與客觀欄
dotnet run --project tools/EvalScorer -- ingest --run docs/eval/runs/2026-10-29 \
    --project "D:\desk\college\cat5201-pro\file\eval-T01-20261029.json"

# ④ 代號化給人盲評
dotnet run --project tools/EvalScorer -- blind --run docs/eval/runs/2026-10-29

# ⑤ 機器計分（不需金鑰、不會花錢、可離線重跑）
dotnet run --project tools/EvalScorer -- score --run docs/eval/runs/2026-10-29
```

**freeze**（事前登錄）寫出十份清單與兩份素材的 SHA-256。
整份實驗的可信度取決於「清單是跑之前就定好的」，而口頭保證沒有用；
雜湊讓任何人事後都能驗證清單一個字都沒改過。
刻意用檔案內容的雜湊而不是只記 git commit——未提交的修改不會反映在 commit hash 上，
那個漏洞正好是這份登錄要堵的。

**ingest**（從存檔取數）直接讀 App 的專案存檔，產生 `outputs/` 與 `metrics.csv`。
為什麼不讓人從決策視窗抄：抄寫會出錯，而且抄下來的數字沒有來源可追。
存檔裡本來就逐筆記了每次執行的實際 token、USD、耗時、選模型方式與實際模型。
三件事因此變成不可能做錯：

- **成本**是 `UsageRecords` 每一筆實際金額的加總，不是解析顯示字串（「約 NT$10.35」）。
- **組別**由存檔推定（`API Auto` → D、手動 + GPT → A、手動 + Claude → B），不由操作者填。
- **第幾次**依實際執行時間排序，所以同一個存檔重跑幾次都得到同一份 `metrics.csv`。

判斷規則放在 `cat5201.Core/EvalRunIngest.cs` 而不是命令列程式裡，並有
`EvalRunIngestTests` 釘住——「哪一筆屬於哪一題、哪一組」是方法論，不是搬資料的細節。
失敗或被中止的執行會自動略過（算不出完整產出的資料留著只會汙染平均），
提示詞對不上任何題目的節點也會略過，所以同一個專案檔裡夾著平常的工作不會被算進實驗。

`docs/eval/runs/_example_smoke/` 是刻意寫壞的假產出，用來證明計分器真的在判斷
（五點只寫三點會扣命中率、先拒答又自己補猜測會踩到禁止內容）。它**不是實驗結果**。

`scores.csv` 的欄位是 `hits / total / hit_rate / critical_ok`，刻意不叫 `coverage` 或 `passed`。

完整的實驗設計、分組、重複次數與分析判準見 [docs/EVAL_PLAN_2026-07.md](../EVAL_PLAN_2026-07.md)。

## 五、同一份清單的另一個用途：內容保留率

`EvalRubric.Retention(spec, before, after)` 用同一份清單比對**壓縮前後的簡報大綱**，
回答「壓到 N 頁之後，必要的東西還在不在」，並列出**失去了哪幾項**。

這把尺也促成了壓縮邏輯的第三次修正。保留依據被連續三輪各打穿一次：

| 輪次 | 當時的規則 | 被打穿的方式 |
|---|---|---|
| 第二輪 | 保留前 N 張，其餘併進尾巴 | 九節壓五頁只剩第 1～3 節，**結論最先被刪** |
| 第三輪 | 均勻取樣＋固定保留最末節 | 結論救回來了，但「均勻取樣仍然只是位置規則」 |
| 第四輪 | —— | 「重要限制若在第四節，仍可能被刪除」 |

現在的順序是**標題語意優先、位置次之**：先挑標題看起來不能刪的章節
（結論／總結／建議／行動／限制／風險／注意／來源／參考），
再用均勻取樣把剩下的額度填滿，並且永遠保留最末節。
所以「風險與限制」不論排在第 4 節或第 8 節都留得住
（`ProtectedSectionsSurviveRegardlessOfPosition`、`AProtectedSectionInTheMiddleIsKept`）。

**仍未解決**：受保護的判準是「標題長得像結論或限制」——系統認得自己產生的章節名字，
認不出使用者心裡真正必要的中性標題。若使用者要的重點掛在「天候判讀」這種標題下，
壓縮時依然可能被犧牲。清單能**量出**丟了什麼，還不能**決定**該留什麼；
要做到後者，得先能從使用者的需求文字裡抽出必要項目清單，那是本專題未完成的部分。

這個限制有一條正面記錄它的測試（`NeutralHeadingsAreStillSacrificed_KnownLimitation`）。
哪天壓縮器會讀清單了，那條測試就會失敗——那時請把它改寫成正向的驗收條件，而不是刪掉。
