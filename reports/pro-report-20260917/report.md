# 摘要

生成式 AI 可協助研究、摘要、寫作及媒體製作，但完成一項包含多個步驟的工作時，使用者仍需要處理資料傳遞、模型選擇、輸出格式與成本辨識。若各階段分散於不同工具，工作規則與來源資訊也不容易一致保留。本專題以此為出發點，設計並實作 cat5201 pro 節點式 AI 工作台。

系統使用 C# 與 .NET 8 開發，以 WPF 提供桌面畫布，並將代理執行、編排計畫、共享工作區及多種檔案產生器分離至 cat5201.Core。使用者可選擇手動、規則自動或 API 自動模式；系統依任務安排能力執行與代理協作，將中間產物整理後交由模型合成答案。產出包含文字、DOCX、PDF、PPTX、XLSX、圖片與影片，並整合 Google Drive 及區域網路手機介面。[1–4]

個人化是本系統的主要設計重點。全域偏好與專案內容分開保存，讓回答方式、技能指示、模型路由、媒體風格、成本門檻及雲端上傳選項跨專案使用。決策視窗則呈現任務判斷、模型選擇、能力執行、備援、使用量及工作區產物，協助使用者了解系統行為。

2026 年 9 月 17 日執行既有自動化測試，204 項通過，0 項失敗，0 項略過。此結果支持測試涵蓋的邏輯與部分整合行為；尚未構成真實 API 成功率、生成品質或多模型優於單模型的證明。目前仍需改善逐呼叫成本歸屬、搜尋失敗狀態、成果版本保留及個人化衝突處理。[5]

## Abstract

This project implements cat5201 pro, a node-based AI workspace that combines task routing, agent collaboration, reusable user preferences, artifact generation, and execution tracing. A WPF desktop interface connects to a .NET core library and multiple external model services. A shared workspace retains intermediate artifacts for synthesis and inspection. Personalization settings are stored separately from projects and influence response instructions, model routing, media styles, and output handling. The existing automated suite passed 204 tests on September 17, 2026. These results verify covered software behavior; comparative model quality and live-service reliability remain subjects for further evaluation.

# 第一章 緒論

## 1.1 研究背景與動機

一項研究型工作通常包含需求釐清、蒐集資料、摘要、分析及文件製作。模型可以完成其中部分內容，但使用者仍須安排前後步驟、保存中間結果，並辨識不同輸出的依據。當任務需要圖片、簡報或影片時，文字模型與專用服務之間的轉接也增加了操作負擔。

本專題關注這些步驟如何在同一個工作環境中被組織與追蹤。節點畫布用來表達任務和內容關係；多模型介接提供不同能力的選擇；共享工作區保存各階段資料；個人化讓使用者不必在每次任務重複輸入相同要求。設計動機是減少重複操作並提高過程可理解性，實際改善幅度仍需使用者評估確認。

## 1.2 專題目標

本專題設定四個主要目標。首先，建置可儲存及重新開啟的節點工作空間，讓內容可以沿連線傳遞。其次，整合模型路由、代理分工與產出流程，使任務能從輸入進展到可使用的成果。第三，將個人化保存為跨專案設定，提供可重用的偏好與技能。第四，呈現執行紀錄、來源與成本估算，讓使用者能檢視及介入過程。[1–4]

## 1.3 研究問題

本專題探討三個問題。其一，如何將不同模型與專用產出服務整合到一致的節點執行流程。其二，如何讓使用者設定工作規則，並在新專案中延續設定。其三，如何呈現足夠的執行資訊，使使用者能理解結果來自哪些處理階段，以及哪些階段發生失敗或降級。

## 1.4 範圍與研究方法

研究採工程實作、原始碼分析與自動化測試方式，對象為 pro 版 1.8.0。系統以 Windows 桌面為主要宿主，手機端為依賴桌面程序的區域網路介面。模型及生成能力來自外部 API，本專題的工作在於流程、介面、資料與控制機制整合，未訓練新的基礎模型。

本報告不將規劃中的完整 Web 客戶端、多使用者雲端同步或程式碼自動套用列為已完成成果，也不將自動化測試通過解釋為模型答案必然正確。

# 第二章 技術背景與設計定位

## 2.1 桌面介面與共用核心

WPF 提供 XAML 介面描述、控制項、版面配置與事件處理，適合建置本專題需要的節點互動與多區域資訊呈現。WPF 為 Windows 平台技術，因此主程式以 net8.0-windows 為目標。Core 專案使用 net8.0，將可重用邏輯與 UI 控制項分離，作為後續其他宿主的基礎。[6]

## 2.2 模型路由與代理協作

本系統以模型登錄資料描述供應商、服務識別碼、能力與成本層級，再由路由器取得對應 Provider。代理則由角色、預設模型、允許能力與委派規則組成。多模型指一次流程可以呼叫不同模型；多代理指不同角色承擔不同子任務。兩者在系統中相關，但不等同，也不保證每次任務都會觸發多模型協作。

代理協作的結果寫入共享工作區，最終合成可讀取其中的搜尋摘要、結構化事實與分析產物。這種設計提供可檢查的中間資料，但其正確性仍受來源、解析規則與模型輸出影響。[2]

## 2.3 結構化文件與手機服務

Office 格式由 Open XML SDK 建立，報告 PDF 由 QuestPDF 產生；因此系統的文件成果是可開啟的實體檔案，而不只是聊天區的格式化文字。Open XML SDK 提供操作 Office Open XML 文件結構的程式介面。[7]

手機鏡像使用 ASP.NET Core 的 Kestrel 伺服器，在桌面程序中提供網頁、快照及指令端點。Kestrel 是 ASP.NET Core 的 Web 伺服器實作；本專題將其用於區域網路互動，並未將它視為已完成的雲端服務。[8]

## 2.4 系統定位

| 工作形式 | 本專題關注的需求 | 對應設計 |
| 純文字對話 | 如何重用前一階段結果 | 節點上下文與附件 |
| 多步驟工作 | 如何安排分工與追蹤狀態 | 編排計畫與共享工作區 |
| 重複性任務 | 如何保存一致的工作要求 | 偏好與技能指示 |
| 多種成果 | 如何交付可使用檔案 | 文件及媒體生成管線 |

此表為設計問題的分類，不是對特定商用工具的功能排名。專題特色應以本系統已實作的整合方式說明，不主張市場唯一性。

# 第三章 需求分析與功能範圍

## 3.1 使用者與主要情境

目標情境包括學生整理課堂資料、研究主題並製作報告，或個人工作者將文字資料轉成多種交付成果。使用者需要 Windows 電腦、網路及所需服務的 API 存取權限；採自備金鑰模式可以分開管理服務帳戶，但初次設定仍有門檻。

核心案例是「輸入主題與附件，取得研究內容，再轉成報告或簡報」。延伸案例包含自訂回答格式、儲存技能、生成圖片與影片，以及透過手機查看與控制任務。

## 3.2 功能需求與目前狀態

| 編號 | 需求 | pro 版實作狀態 |
| F01 | 建立與連接節點並保存專案 | 已接線，含位置、內容及連線狀態 |
| F02 | 選擇模型與任務模式 | 手動、規則自動及 API 自動 |
| F03 | 代理分工與中間資料共享 | 執行核心及共享工作區已實作 |
| F04 | 個人化跨專案保存 | 偏好、技能、路由及產出設定 |
| F05 | 文件與媒體成果 | DOCX、PDF、PPTX、XLSX、圖片、影片 |
| F06 | 手機控制與 Drive 整合 | 區網手機介面及 Drive 讀寫已接線 |
| F07 | 使用者控制與執行追蹤 | 產出確認、停止、重跑及決策紀錄 |

「已接線」指可由程式主流程呼叫，外部服務仍取決於金鑰、權限與 API 狀態；不代表本次已重新完成所有真實服務測試。

## 3.3 非功能需求

可靠性要求包括避免一次錯誤使整個程序無聲終止、保留可診斷日誌，以及維持舊資料相容。可理解性要求包括狀態、模型與成果資訊可以被使用者辨識。可維護性要求則是盡量讓執行邏輯透過介面與桌面 UI 分離。

對安全與成本的要求為本機金鑰加密、手機端權杖驗證、產出確認與預算門檻。這些機制降低部分風險，但目前不是具備完整租戶隔離、雲端身分管理與精確帳務結算的服務。

# 第四章 系統架構與資料設計

## 4.1 三專案結構

!DIAGRAM architecture

圖 4 1　pro 版主要模組與資料流向

WPF 主專案包含 MainWindow、NodeControl、NodeService、Provider 介接及手機伺服器。MainWindow 管理畫布、專案與全域設定，NodeControl 處理節點輸入、輸出、狀態及使用量。NodeService 串起桌面節點與執行核心。[1,3]

cat5201.Core 包含 AgentRuntime、編排計畫、能力層、工作區、資料契約、產檔器及部分外部服務。核心透過 IAgentHost、INodeContext、IExecutionDecisionResolver 與 IDecisionFinalizer 取得宿主功能，並由委派呼叫實際模型執行。測試專案以假宿主與假 Provider 驗證核心可被獨立呼叫。[2,5]

## 4.2 解耦程度與設計取捨

AgentRuntime 本身不需要引用 WPF 控制項，但正式桌面實作的上下文組裝、模型選擇與部分設定仍在 WPF 專案。Core 內的金鑰與 Google token 儲存也使用 Windows DPAPI。因此目前達成的是執行核心抽象化，不是整個應用已能跨平台部署。

桌面直接呼叫 Core 可以降低遷移成本；未來若建立正式 API 宿主，仍需提供非 WPF 的宿主、決策及模型執行實作，並處理每位使用者獨立的設定與帳本。

## 4.3 專案與工作區資料模型

專案檔保存使用者可以再次開啟的工作空間；AgentWorkspace 保存一次執行過程的中間產物。兩者生命週期不同：畫布會持久化，工作區在執行時建立，部分摘要與產物紀錄再寫入節點執行歷史。不能將畫布重新載入直接視為完整恢復所有執行中的狀態。

| 資料類型 | 主要欄位或內容 | 用途 |
| NodeState | 識別碼、座標、大小、輸入輸出、模型、任務 | 還原節點 |
| ConnState | 起點、終點、接點位置、FlowMode | 還原關係與流動模式 |
| AttachmentState | 所屬節點、名稱、相對路徑、類型 | 連結專案附件 |
| ExecutionLogState | 模型、時間、使用量、備援、產物 | 保存執行紀錄 |
| AgentWorkspaceItem | 類型、來源代理、payload、時間 | 保存執行中間資料 |
| GeneratedFilePayload | 路徑、格式、成功狀態、錯誤 | 描述實體成果 |

## 4.4 資料關係與版本相容

AppState 將節點、連線、附件與執行紀錄集合保存為 JSON。格式包含 SchemaVersion；舊檔案缺少版本欄位時可使用預設值載入。偏好資料則另外保存，不因開啟其他專案而替換目前的全域設定。[3,4]

AgentWorkspace 使用鎖保護集合操作，並可依型別取得產物。產物摘要會推導狀態、來源、依賴與可見性，供決策視窗呈現。這是一種執行追蹤資料結構，而非防竄改稽核帳本；依賴資訊也不是所有步驟都具備完整事件溯源。

## 4.5 儲存布局

專案根目錄下的 JSON 對應畫布；_attachments 保存附件，_generated 保存成果，_config 保存偏好、金鑰、帳本與影片任務紀錄，_memory 保存記憶資料。實際位置由主程式決定，目前優先使用既有開發資料目錄，否則使用 LOCALAPPDATA 下的應用資料位置。

集中配置資料位置使相關檔案能一起管理，但成果路徑及附件相對路徑的搬移仍須考慮專案重新命名與跨機器使用。ProjectStore 已提供重新命名、備份處理及附件資料夾搬移邏輯。

# 第五章 任務路由與多代理執行

## 5.1 一次節點執行的生命週期

!DIAGRAM execution

圖 5 1　節點執行的主要階段

使用者送出內容後，節點檢查預算並建立可取消的執行範圍。NodeService 先解析輸出意圖，再建立含節點、代理、偏好與工作區的 AgentExecutionRequest。AgentRuntime 解析決策、規劃能力順序，將研究或附件結果寫入工作區，必要時進行代理協作，再合成答案及產出成果。[2,3]

輸出意圖由模型判斷報告、表格、簡報、圖片與影片需求；解析失敗時使用關鍵字備援。目前關鍵字與語意判斷仍共同影響路徑，並非所有情況都由單一語意結果決定。根節點若被判定需要產出，會進入確認流程；手動模式也可在使用者同意後生成檔案或媒體。

## 5.2 狀態機與結果呈現

編排計畫包含任務辨識、流程選擇、代理與模型選擇、能力執行、工作區寫入、最終合成及產出階段。各階段使用 pending、running、success、failed 或 skipped；整輪另外可呈現 partial。這讓部分能力失敗與整輪失敗可以有不同紀錄。

狀態是否準確仍取決於每個呼叫點的標記方式。例如文字合成成功而文件生成失敗時，應同時保留文字成果及產出錯誤，而不是僅以「有文字」概括全部成功。

## 5.3 模型選擇與備援

| 模式 | 決策來源 | 使用方式 |
| 手動 | 使用者選擇的代理、模型及任務 | 明確指定工作方式 |
| 規則自動 | 任務關鍵字與路由規則 | 依規則選任務及模型 |
| API 自動 | 模型分類搭配代理規則 | 語意判斷後選擇執行方式 |

使用者自訂的任務路由可覆蓋 API 推薦；能力守門檢查附件、圖片、搜尋與串流需求，必要時調整模型。備援候選依主模型、同供應商替代、任務偏好及可用模型建立。這表示手動模式保留的是主要選擇意圖，仍可能受能力相容性或備援規則影響，不能宣稱永不切換模型。

目前登錄包括 GPT-5.6 Sol、GPT-6 Astra、Claude Sonnet 5、Claude Opus 5、Perplexity Sonar 與 Deep Research、Gemini 3.5 Flash 及 3.1 Pro。這是目前程式的模型配置，並非外部服務可用性的重新驗證。舊模型選擇可轉換為後繼模型，並另設歷史顯示名稱對照。[2]

## 5.4 代理分工與共享工作區

一般、研究、翻譯、程式及圖片代理具有不同角色設定；報告、表格與簡報還有產出專責角色。API 自動模式可以依任務規劃平行子任務，子代理共享工作區，再由根任務合成。委派深度受限制，以避免無限遞迴。

這些角色是應用程式定義的執行設定與提示規則，並不是另外訓練的模型。簡單任務可由單一模型完成；平行與委派的條件目前含關鍵字規則，可能增加重複研究與呼叫成本，仍需效果評估調整。

## 5.5 事實與分析的區分

研究流程可建立 search_summary 與 verified_facts，記錄來源、時間、事實類型及可信度資訊。最終提示會優先採用結構化事實，避免自由分析文字覆蓋數值。金融研究另區分收盤、盤後與盤前資料，並偏好正式財報來源。

這是降低資料混用的設計措施，不是形式化驗證。來源標記與欄位仍可能由模型或解析規則產生，必須保留原始來源供人檢查；搜尋服務失敗時的降級狀態也是後續需加強的部分。

# 第六章 個人化與記憶設計

## 6.1 個人化的設計目標

個人化的目標是讓使用者保存長期工作習慣，並在執行時影響回答、模型與成果處理。系統將個人化與專案資料分開，避免開啟舊專案時把目前習慣覆蓋。這使「使用者如何工作」與「某一專案包含什麼內容」成為兩種不同資料。[4]

個人化可分為四層。表達層設定語言與格式；任務層保存技能及模型路由；資源層設定高成本模型、預算與逾時；交付層設定簡報生成器、影片風格及 Drive 上傳。這些層次同時涵蓋提示詞與確定性的程式設定。

## 6.2 全域設定的生命週期

設定變更後，SavePreferences 將 UserPreferencesState 序列化至 _config/_preferences.json。啟動時 LoadPreferences 載入資料，再同步到模型成本政策、路由設定與 SkillsRegistry。欄位提供預設值，使舊偏好檔在缺少新欄位時仍能載入。

新使用者的預設包括每日預算 NT$100、產出確認自動同意秒數為 0、上游附件繼承關閉及影片模型檔位 Lite。每日預算是新任務啟動前的門檻，並不是供應商端的即時扣款上限；已啟動工作及並行請求仍可能使總額超過門檻。

## 6.4 偏好與技能的差異

偏好適合保存長期表達要求，例如繁體中文與結論優先；技能適合保存可重複的工作程序，例如研究報告需包含摘要、來源與限制。使用者可以新增、編輯、停用及刪除技能，也能從 GitHub 文字連結匯入，解析 SKILL.md 的名稱與正文。

目前技能的執行方式是文字提示注入。匯入檔案不會自動安裝程式、執行 shell 腳本或取得其他工具權限，因此報告將其稱為可重用工作指示。啟用技能對模型輸出的影響仍需要觀察，不能等同硬性程式規則。

## 6.5 個人化的展示與驗證

可使用相同研究問題進行設定前後比較：先保留預設，再加入「繁體中文、先寫結論、解釋專有名詞」及研究技能。比較輸出是否符合要求，並在新專案重試，以區分單次提示效果與跨專案保存效果。

若節點明確要求英文或取消條列，應檢查局部指示是否能覆蓋全域偏好。程式目前存在不同提示區塊對優先級描述不完全一致的情況，因此此項應列入語意驗收，而非僅靠偏好檔 round-trip 測試。

## 6.6 記憶的類型與召回

MemoryStore 使用本機 JSON 保存記憶。偏好以鍵值更新，同類偏好保留最新內容；使用者也可以明確將節點加入記憶。執行結果、能力軌跡與工作區摘要另有情節型紀錄，用於後續召回。這是以規則與文字相關性為基礎的記憶設計，並未使用向量資料庫。[4]

NodeMemoryService 將偏好與一般記憶分開處理。偏好獨立注入；情節記憶會依專案、代理及查詢條件篩選，並以同一條有向鏈的節點為主要範圍，降低兄弟分支詳細內容混入的機會。使用者明確標記的記憶可跨鏈使用；要求統整整個畫布時另有放寬路徑。

一般上下文仍可能包含其他支線的低權重摘要。因此跨鏈隔離的意義是限制詳細記憶召回，不代表其他節點資訊完全不會出現在提示中。這個區分對解釋系統如何理解畫布很重要。

## 6.7 規則衝突與透明度

設計上希望目前節點的明確要求優先於背景資訊，偏好及技能提供預設行為。然而，目前部分最終合成提示將偏好描述為最高優先，與其他區塊存在張力。後續應集中管理優先順序，並提供「本次套用的設定」摘要，讓使用者知道哪些偏好、技能、路由及風格影響了結果。

| 驗證案例 | 預期判準 | 目前證據 |
| 載入舊偏好檔 | 新欄位使用安全預設 | 已有自動化測試 |
| 停用技能 | 不出現在技能提示區塊 | 已有自動化測試 |
| 新專案沿用設定 | 全域設定維持一致 | 有儲存載入機制，需 UI 驗收 |
| 本節點與偏好衝突 | 按明確優先序處理 | 需補語意測試 |
| 影片自訂風格 | 自訂文字進入生成提示 | 有解析邏輯及部分測試 |

## 6.8 個人化的工程意義

本專題的個人化貢獻在於把設定接入執行與產出流程，而非只保存介面外觀。這提供可重用工作方式的基礎。其後續價值應透過指令遵守率、設定重複輸入次數與使用者操作時間量測，避免僅以設定項目數量評估完成度。

# 第七章 畫布操作與內容產出

## 7.1 節點與連線

節點包含上方輸入與下方結果，並可調整位置、大小與模型等設定。一般連線表達上下文關係；流動連線用於自動往下執行。系統提供建立下游節點、停止、略過與重新執行等操作，並以等待、執行、成功及失敗狀態回饋使用者。[3]

工作流執行包含沿第一個下游的鏈式路徑，以及沿流動連線扇出的路徑。後者在父節點完成後啟動多個子分支，並使用已訪問集合避免同輪重複執行。此設計適合分支工作；多個上游再匯合到同一節點時，仍需另外驗證是否等所有必要輸入完成，不能直接視為完整的 DAG 排程器。

## 7.2 上下文組裝

NodeContextService 依模型策略建立完整、精簡搜尋或研究上下文，組合主鏈上下游、支線摘要及附件提示。內容以字數和深度限制控制大小；主鏈與目前節點較優先，支線用來提供背景。

部分主鏈取得邏輯採第一條入邊或出邊，而非自動合併所有父節點。因此展示時應讓資料依賴清楚，不把多條連線一概解釋成所有內容都已完整合併。長鏈也可能因截斷而遺失前文細節。

## 7.3 附件讀取與成本控制

附件可由本機加入，也可從 Google Drive 選取。AttachmentTextCache 將 PDF、HTML、Office 及部分文字格式在本機抽取為文字，以路徑、檔案長度及修改時間做快取鍵，減少重複抽取。單一附件文字上限為 60,000 字元，超出會截斷並標示。

圖片維持視覺輸入；抽取失敗的檔案交回 Provider 處理。掃描 PDF 或複雜排版可能無法取得完整文字，系統不能保證所有附件皆可無損理解。預設不繼承上游原始附件，使用者可以自行開啟，以取捨資訊完整度與呼叫成本。

## 7.4 串流與取消

主要 Provider 支援回覆接口，OpenAI、Claude 與 Perplexity 具有串流處理；目前 Gemini 的串流接口實際上等待完整結果後一次推送。節點透過取消權杖處理手動停止及逾時。串流已輸出部分內容後，備援策略避免直接混入另一模型的答案。

## 7.5 報告與表格生成

主合成完成後，報告作者可將素材改寫為書面內容；表格作者整理 Markdown 表格。DOCX 與報告 PDF 使用同一份報告文字；XLSX 與表格 PDF 使用對應表格材料，降低跨格式內容偏離。GeneratedFileWriter 負責命名、寫檔及建立產物描述。

目前 XLSX 以文字儲存格輸出為主，適合資料整理與交付，並非通用的公式建模或計算引擎。PDF 使用指定的中文字型；文件能開啟與文字可讀已有部分測試，但不代表每種長篇內容、表格寬度與圖片布局都已完成視覺驗收。

## 7.6 簡報生成

簡報流程可先取得研究材料，再由作者產生結構化投影片內容，轉成 PPTX 與對應 PDF。使用者可要求頁數與配圖，系統具備頁數修整、封面及內容頁插圖等邏輯，也提供單頁重新生成入口。內建 PptxBuilder 作為實體檔案產生器，Gamma 另有生成、輪詢、下載與備援接線。

目前簡報不自動拆成多個下游產製節點，因母節點本身已包含完整流程；重複拆分可能導致每個節點重新生成整份簡報。這是依實際行為作出的流程簡化，而非所有任務都必須展開成長鏈。

## 7.7 產物追蹤與預覽

| 成果 | 主要組件 | 交付方式 |
| 報告 | DocumentAuthor、DocxReportBuilder、PdfReportBuilder | DOCX 與 PDF |
| 表格 | XlsxReportBuilder | XLSX 及表格 PDF |
| 簡報 | PresentationAuthor、PptxBuilder、DeckPdfBuilder | PPTX 與 PDF |
| 來源包 | NotebookLmBundleBuilder | 可匯入的文字檔 |
| 圖片 | OpenAIImageService | 本機圖片與節點預覽 |
| 影片 | VeoVideoService、FfmpegService | MP4 與生成紀錄 |

節點以檔案入口及圖片呈現成果，工作區記錄來源、格式與狀態。NotebookLM 目前是文字來源包匯出，並非原生音訊生成整合。成果版本管理仍待改善：重新生成前清除舊檔的流程，應改為新版本成功後才替換，避免失敗時失去上一版可用內容。

## 7.8 圖片生成與編輯

圖片生成將使用者描述整理為生成提示，再呼叫 OpenAI 圖片服務。若有圖片附件且判斷為編輯需求，則走改圖路徑。圖片也可用於報告與簡報配圖，或作為影片連貫模式的起始畫面。結果與相關費用估算寫入節點及工作區。

## 7.9 影片導演與生成模式

影片流程先使用主合成內容作為企劃底稿，再由導演步驟產生分鏡與場景提示。連貫模式可先生成靜態起始圖，交給 Veo 生成基底影片，再依支援情況延伸；快剪模式則生成多個獨立片段，以 ffmpeg 裁切及拼接。

| 模式 | 系統流程 | 限制與降級 |
| 連貫 | 起始圖、基底影片、逐段延伸 | 依檔位支援；失敗保留部分成果 |
| 快剪 | 各鏡頭生成後裁切拼接 | 上限六鏡頭；需本機 ffmpeg |
| 導演計畫 | 分鏡與提示文字 | 未配置影片服務時仍可交付計畫 |

程式中的長度規劃以基底 4、6 或 8 秒及延伸每段 7 秒等規則處理，目標上限為約 148 秒。這些是當前實作的限制與配置，真實服務接受的參數仍需依執行結果確認。Lite 檔位的連貫模式不做延伸；沒有 ffmpeg 時快剪降級為連貫流程。

## 7.10 風格個人化與長任務恢復

影片風格分為導演閱讀的完整美學描述，以及送入 Veo 的精簡視覺標籤。目前預設為當代大畫幅電影攝影、清晰材質、自然光與沉穩運鏡；使用者可自訂覆蓋。模型提示不使用參考作品名稱，以減少把固定人物或場景帶入不同主題。

VideoJobJournal 在 operation 建立後記錄識別碼，重新啟動時可查找近期未完成任務，提供繼續輪詢與下載的機會。這是單一雲端任務恢復，不等於完整還原多鏡頭工作流。Kling、配音及配樂仍有未完成接線的部分，不列為已驗證的完整產出能力。

# 第八章 跨裝置整合與資料管理

## 8.1 手機鏡像與控制

MobileMirrorServer 在桌面程序中啟動 Kestrel，預設監聽 5201 埠。每次啟動產生 128 位元隨機權杖，手機以帶權杖的網址連線。桌面定期發布工作區快照，手機頁面輪詢更新；目前不是 WebSocket 或 SSE 即時推送。[8]

| 端點 | 功能 | 存取條件 |
| GET / | 手機頁面 | 需權杖 |
| GET /api/snapshot | 節點及工作區摘要 | 需權杖 |
| GET /api/node/{id}/text | 單一節點全文 | 需權杖 |
| POST /api/command | 停止、重跑及其他支援指令 | 需權杖 |
| GET /api/ping | 連線健康檢查 | 不需權杖，只回傳 ok |

手機功能包括查看狀態與全文、停止或重跑、建立指令節點、選擇模型及上游，以及回應產出確認。指令由桌面 Dispatcher 交回 UI 執行緒處理。手機仍依賴桌面程式運行與區網可達，未提供獨立帳戶或完整畫布編輯。

## 8.2 Google Drive 整合

GoogleDriveService 處理 OAuth 授權、檔案列表、下載、匯出及上傳。一般檔案可作為附件；Google Docs、Sheets、Slides 透過匯出轉成文字或 CSV，再進入既有附件流程。Drive API 支援上傳內容及轉換為 Google Workspace 文件等處理方式。[9]

GeneratedFileWriter 的產出後鉤子依個人化設定決定是否上傳，並可按 PDF、Word、簡報、Excel、圖片、影片及文字分類控制。DOCX 與 XLSX 可選擇轉成 Google 文件或試算表。上傳在背景執行，失敗目前主要寫入日誌，使用者可見的重試及狀態呈現仍需加強。

## 8.3 應用邊界

區網 HTTP 加上權杖適用於目前鏡像情境，不能直接當成已完成網際網路部署安全設計。若開放遠端公開存取，需另做加密傳輸、使用者認證、權限、速率限制與部署管理。Google 連結成功也不代表所有雲端檔案都能讀取，仍受授權範圍及服務權限影響。

## 8.4 本機資料與金鑰

API 金鑰由環境變數或使用者設定取得，使用者輸入的金鑰以 Windows DPAPI CurrentUser 加密保存。這降低明文落地風險，但同一使用者權限下的程序仍可能取得解密能力；加密檔也不適合直接跨機器複製使用。

「本機保存」不表示「內容不會離開本機」。模型請求會將提示與所需附件內容送到選用的外部服務，Google Drive 上傳也會傳出成果。展示時應遮蔽金鑰、帳號與私人資料，並讓使用者理解資料流向。[1,4]

## 8.5 存檔與失敗恢復

AtomicFile 先寫暫存檔，再以替換方式更新主檔並保留 .bak。若替換遇到 I/O 錯誤，程式重試後可能退回複製覆寫；因此這條降級路徑不具相同的原子性保證。ProjectStore 載入主檔失敗或 JSON 毀損時，可退回備份；偏好與其他資料的恢復行為則需依各自載入邏輯判斷。[3]

主程式另保存會話標記及最後專案位置，偵測未正常關閉後可提示重新開啟。這能恢復已保存專案，不代表尚未落地的生成內容完全不會遺失。全域例外處理與 AppLog 則留下診斷資訊，協助辨識背景及 UI 錯誤。

## 8.6 成本帳本與使用者確認

SpendLedger 以日期累加美元估算，保存近期帳本並提供台幣顯示。節點將 API usage 與媒體費用分開累加，產出確認框也展示輸出類型與費用提示。沒有 usage 時可退回文字量估算。

目前 token 彙總後可能套用最終模型的價格，輔助呼叫未必完整歸帳；快剪影片以成品秒數計算時也可能低於生成素材的成本。正確的後續方向是逐次記錄模型、用途、token、生成量與單價，再向上彙總。報告將現況稱為成本估算，不宣稱與供應商帳單完全一致。

## 8.7 打包與維護

publish.ps1 提供 Windows x64 自含式發行流程，GitHub Actions 定義建置與測試。實際散布仍需確認 WebView2、ffmpeg 與字型等環境需求。專案保留 LICENSE 與第三方元件清單；散布條件應依實際版本與使用情境確認，本報告不將打包完成等同完整商業交付驗收。

# 第十章 限制與改善方向

## 10.1 可信度與資料品質

搜尋能力目前會在服務失敗時回傳帶警告的摘要，使主流程繼續。核心若只檢查摘要是否存在，可能無法正確區分已取得新資料與降級回答。後續應以明確狀態描述搜尋成功、空結果、服務失敗及資料過期，並在答案與決策視窗一致呈現。

verified_facts 是結構化來源資料的名稱，不代表每筆內容都經過獨立驗證。引用、數值與來源日期需要更嚴格的對應檢查；金融研究中寫死的示例與時點也應定期檢視，避免舊提示影響新任務。

## 10.2 成本與成果保護

成本應由每次 API 呼叫各自計算，再彙總到步驟、節點及專案。媒體費用應根據實際生成素材與供應商計費單位處理，不能只依成品長度。預算控制可進一步採保留額度及每步檢查，避免多個任務在同一門檻下同時啟動。

重新生成應保留前一版成果，待新版本成功再切換目前版本。工作區紀錄需要指向對應檔案版本，並提供失敗回復與清理機制，避免重跑導致舊檔遺失或留下失效連結。

## 10.3 架構與工作流

MainWindow 與 AgentRuntime 仍承擔大量責任。可先將工作流排程與各種產出管線分成獨立服務，再以現有測試保護行為。若要支援正式 Web 端，還需分離靜態全域設定、每位使用者狀態、儲存及 Provider 宿主，不能直接把桌面鏡像公開上線。

目前流程較偏單節點原子執行與分支鏈；完整步驟恢復、跨節點匯流、依賴檢查及冪等控制仍需補強。程式代理限快照、差異與驗證，尚未提供受控的來源檔套用。

## 10.4 改善優先順序

| 優先 | 改善項目 | 驗收方式 |
| 第一階段 | 搜尋狀態、成本明細、成果保留 | 失敗與計費回歸測試 |
| 第二階段 | 個人化優先序與作用摘要 | 固定衝突題組與 UI 驗收 |
| 第三階段 | 工作流依賴與核心拆分 | 多分支及取消情境測試 |
| 第四階段 | 使用者評估及多模型比較 | 預先定義題組與盲評 |
| 後續階段 | 正式 API 與完整 Web 客戶端 | 獨立宿主及多使用者驗證 |

# 第十一章 結論與專題貢獻

## 11.1 研究目標達成情形

cat5201 pro 已建立以節點為核心的 AI 工作環境，將模型選擇、代理協作、共享資料與多種成果產出接在同一流程。個人化設定可跨專案保存，手機與 Drive 則提供延伸操作及交付入口。既有自動化測試支持部分核心規則、資料相容與整合行為。

| 目標 | 已完成成果 | 尚待補足 |
| 組織多步驟工作 | 節點、上下文、流動連線及控制操作 | 複雜匯流與細粒度恢復 |
| 整合模型與產出 | Provider、代理、文件及媒體管線 | 真實服務可靠性量測 |
| 保存個人化方式 | 全域偏好、技能與模型路由 | 衝突規則與語意驗證 |
| 提高過程可理解性 | 決策紀錄、工作區與成本估算 | 更準確的狀態與費用歸屬 |

## 11.2 主要工程貢獻

第一項貢獻是節點與執行流程的整合，讓使用者能以可視方式組織任務並重用上游內容。第二項是多代理共享工作區，將中間資料與最終成果區分並保留來源資訊。第三項是個人化生命週期，讓偏好、技能與控制設定從儲存延伸至執行。第四項是桌面、手機、文件與雲端服務的整合，以及相容性、恢復和測試基礎。

以上為本系統的工程設計與實作成果，不主張提出新的基礎模型、訓練演算法或已證明優於既有框架的代理方法。生成內容本身由外部模型及服務提供，系統貢獻在於如何安排、控制、保留與交付這些能力。

## 11.3 後續研究方向

後續重點應是以可重複證據說明哪些任務適合協作，以及個人化是否降低重複操作並提高指令遵守。這需要固定題組、逐呼叫記錄、來源核對及使用者回饋。完成可信度與成果保護後，再擴充正式 API 宿主與 Web 介面，較能維持功能與可靠性的一致發展。

本專題的展示重點可歸納為：使用者能設定工作方式，查看執行過程，並取得可使用的成果。這三者的連結，是 pro 版目前最具體且可展示的價值。
