# cat5201-pro：專案評價、改善順序與十分鐘專題展報告

檢查日期：2026-09-24。對象：目前工作目錄的 1.8.1-pro，包含尚未提交的修改。

## 1. 評價與證據邊界

這個專案有資格成為求職作品集的主力：它已有可操作的桌面介面、跨服務編排、檔案交付、個人化、記憶、成本紀錄和測試。最有說服力的貢獻是把不穩定、會花費、需要上下文的 AI 呼叫，整合成使用者能設定、查看和介入的工作流程。

目前較弱的是成效驗證與失敗時的可靠性。功能廣度已足夠；继续增加供應商或產出格式，對專題說服力的幫助可能小於一組可信的對照實驗、一次失敗恢復展示，以及清楚的工程取捨。

本次重新檢查版本差異、主執行流程、畫布排程、上下文與記憶、個人化、搜尋狀態、成本計量、文件技能、手機介面及相關測試與文件；屬程式與文件審查，並非逐項真人操作驗收。執行 `dotnet test tests/cat5201.Tests/cat5201.Tests.csproj --no-restore --verbosity minimal`：249 通過、0 失敗、0 略過。未呼叫付費 API、未驗證所有供應商即時相容性、未人工檢視本次生成文件。測試通過不能換算成 AI 回答正確率或使用者成功率。

| 面向 | 目前評價 | 要再提升所需證據 |
|---|---|---|
| 應用整合 | 明顯有深度；已有跨服務與產物流程 | 可重現安裝與完整案例 |
| 工程結構 | 已有 Core、介面、假件測試，仍有大型類別與 UI 耦合 | 排程器、上下文政策與執行狀態可獨立測試 |
| 個人化 | 是適合主打的方向，範圍超過語氣設定 | 偏好遵守、局部覆寫、刪除後不再召回的實測 |
| 可靠性 | 已做不少防禦，但仍有會破壞信任的邊界問題 | 失敗保留產物、分支匯流、成本上限測試 |
| 新穎性 | 整合與使用體驗有價值；不能僅靠畫布或多模型宣稱獨創 | 明確使用者、差異化流程、比較證據 |
| 比賽準備 | 展示素材豐富，驗證故事不足 | 對照實驗與外部試用 |
| 求職準備 | 適合 AI 應用／.NET／軟體工程作品 | 個人責任、設計決策、測試、缺陷修復記錄 |

以上是依目前程式的質性判斷，不是競賽名次、市場排名或錄取預測。

## 2. 值得介紹的實際貢獻

1. **個人化介入不同階段。** 偏好與明確記憶影響上下文；模型限制與成本設定影響路由；文件引擎與影片風格影響交付。應展示「設定 → 實際行為 → 可查看的依據」，而不是逐頁介紹設定面板。
2. **執行過程能被查看。** 決策、來源、實際模型、工作區產物與花費使使用者有機會理解執行過程。用「執行紀錄／決策摘要」較準確；不是模型內部思考的完整還原，也不是防竄改審計系統。
3. **交付可編輯文件。** 研究與回答能走到 DOCX／PPTX／XLSX／PDF，且有不同產出引擎。這讓專題能以一項完整工作衡量，超過聊天展示。
4. **工程上開始把 UI 與執行核心分開。** `IAgentHost`、`INodeContext` 與假 Provider 的整合測試適合用於面試，說明如何讓需要外部 API 的系統可測。
5. **失敗狀態與成本資訊正在變得誠實。** 新增 FreshDataAssessment 區分搜尋失敗、無結果與可用資料；UsageMeter 逐呼叫記錄模型與用途；診斷包協助問題回報。這些比再多一個模型選單更能表現工程成熟度。

本次新增的 Claude 官方文件技能與使用者匯入的文字技能是兩種不同機制，報告時要分開說。文件品質同時來自外部服務與你的流程整合，不應把外部模型／技能能力全歸為自行研發。

## 3. 優先改善的問題

### P1：重跑先刪除舊產物

證據：`NodeControl.xaml.cs:1585` 呼叫 ClearOutputFiles；預算檢查在 `1613`。ClearOutputFiles 在 `968` 起會刪除實體檔案。

情境：已有成功報告 → 再次執行 → 預算已達上限或 API 失敗 → 新檔沒有完成，舊檔也已刪除。這是靜態路徑確認，尚未用 UI 重現。

改善：每次執行有 runId 與獨立產物目錄；新產物通過驗證後才切換「目前版本」。失敗保留前一次成功結果；清理版本由明確操作或保留政策處理。

驗收：成功一次後，分別模擬預算拒絕、逾時、取消及 API 失敗，確認舊檔內容、連結與版本仍可用。

### P1：畫布分支匯流尚不具完整依賴語意

證據：`MainWindow.xaml.cs:6112` 用 visited 防止重複執行；`6151` 由每一分支遞迴執行下游。`NodeContextService.cs:328` 的 CollectUpstream 僅取第一條入邊；`MainWindow.xaml.cs:5699` 的輸入注入也只取第一個上游。

情境：A 同時啟動 B、C，B、C 都流向 D。B 先完成即可啟動 D，沒有等待 C 的依賴屏障；另一分支再到 D 時會被 visited 略過。圖看起來能合併，不代表執行資料已完整合併。

改善：短期明確限制流動工作流為樹狀並阻擋多父匯流；需要一般 DAG 時，以每個節點尚未完成的父節點數量排程，定義父失敗、取消、重跑與輸入合併順序。

驗收：菱形圖使用延遲不同的假節點，D 必須只跑一次且收到 B、C 的成功輸出；父失敗時採明確政策。這是排程測試，不能以 API 回答看起來正確代替。

### P1：每日上限仍是啟動門檻

證據：`MainWindow.Spend.cs:122` 檢查當日已花金額；UsageMeter 在呼叫完成時記帳。新的文件技能可在多轮請求中持續執行，沒有在該迴圈看到每日預算預留。

情境：剩少量預算仍能啟動昂貴任務；數條平行分支也可能同時通過檢查。成本記錄準確度提升，不等於上限已被強制保證。

改善：先把文字改成「達額後阻擋新任務」，避免保證絕不超支。再做任務預估、預算預留、每次付費呼叫前檢查及超額確認；未知費用與無法中止的遠端工作要明示。

驗收：兩個並行任務競爭最後一筆額度，不能各自無條件通過；取消後費用仍按已發生呼叫記錄。定價表、快取、搜尋／沙盒費及匯率均須有版本，成本應稱估算，不能承諾與帳單完全一致。

### P2：個人化覆寫規則不一致

證據：`NodeMemoryService.cs:502` 明定節點輸入優先；`NodePromptBuilder.cs:114` 也如此。但 `cat5201.Core/DocumentEngine.cs:96` 把個人化寫成最高優先，AgentRuntime 亦有偏好最高優先的指示。

情境：全域繁體中文，但本次要求英文簡報；聊天與文件產出可能遵守不同指示。這是提示規格衝突，尚未量測模型實際出錯率。

改善：集中生成有效設定，明定「本次明確要求 > 專案設定（若有）> 全域偏好 > 系統預設」，並把資料內容與控制指令分開。對合法格式／語言偏好採此順序；不可讓來源文件覆蓋執行權限。

驗收：同一矩陣測聊天、整合回答、文件：全域繁中／本次英文、全域條列／本次文章、記憶刪除、無關分支隔離，並在決策窗顯示本次生效值與來源。

### P2：文件品質目前部分依賴提示要求

Claude 文件技能提示要求轉圖檢查，但 `ClaudeDocumentSkillsService.cs:218` 附近下載交付檔，成功判定主要依是否有檔案；這不構成本機可驗證的版面品質保證。AgentRuntime 有按類型處理與退回內建的流程，但仍需成品驗收。

改善：檔案可開啟、必需格式存在、頁數與資料一致性是自動檢查；中文缺字、溢出、裁切等用轉圖驗收。記錄 requested／produced／validated／failed，不把取得非空檔案等同任務完全成功。

### P2：功能文件與實作不同步

Known Limitations、Eval 計畫有舊模型與舊狀態；手機伺服器類別註解仍寫唯讀，但已存在指令處理。這會造成簡報、README 與實際演示互相矛盾。

改善：建立版本功能表：已實作、已以假件測試、已真實 API 驗證、尚未接通。以發布版本固定影片與文件，記錄日期、模型、引擎與執行方式。

## 5. 補上哪些實驗最有價值

### 個人化評估：優先做

先固定 12 個情境，每個用開／關個人化兩種條件，各跑 3 次，共 72 次，先用少量案例估成本再執行。涵蓋語言、格式、局部覆寫、修改偏好、刪除記憶、分支隔離。固定資料、基礎模型與任務提示；測試者不得知道條件。二元規則可程式檢查，內容品質由至少兩位評分者依同一規準評分。

記錄偏好遵守率、當次指示遵守率、誤用記憶次數、人工修改時間、花費與耗時。將「格式遵守」與「內容正確」分開，不能只因用了繁體中文就判整體成功。

### 多模型評估：分離兩個問題

同工具權限的固定單模型流程 vs 自動編排流程，評估編排本身；另外以一般使用者原本操作方式 vs 本產品，評估整體工作效率。不要把「有搜尋的多模型」對比「無搜尋單模型」，再把差異全歸功於多模型。

可先用 8 個固定任務、每組 3 次做探索性比較，記錄所有成功與失敗，不預設應贏。報告每類任務的交付成功率、品質、時間與成本，避免用單一平均掩蓋昂貴或失敗案例。小樣本結果只作初步證據。

### 試用與故障測試

邀 5～8 位符合目標情境的同學作形成性試用，不當作代表市場的統計樣本。請他們自行完成任務，不先教每個操作；記錄首次成功時間、求助次數與卡點。故障測試則使用假 Provider，不花 API 費用，涵蓋 429、逾時、取消、缺額度、缺產物與匯流。

## 7. 兩分鐘影片分鏡

以同一份固定且有來源的校園活動資料包，製作活动提案和簡報。既能呈現研究與文件，也不依賴不斷變動的財經數據。不要在影片中切換大量互不相干的任務。

| 片內時間 | 畫面 | 解說方向 |
|---|---|---|
| 0:00–0:15 | 任務與資料附件 | 「這次我要把資料整理成可交付的活動提案。」 |
| 0:15–0:35 | 已存的繁中、先結論、文件引擎等設定 | 「這些偏好會持續生效，執行方式也能由使用者決定。」 |
| 0:35–0:55 | 畫布、任務執行、必要的生成確認 | 「研究內容會交給後續步驟；需要產檔時有確認環節。」 |
| 0:55–1:15 | 決策窗、來源與費用明細 | 「我能查看實際使用的模型與資料，以及含估算的花費。」 |
| 1:15–1:40 | 開啟實際 PPTX／DOCX | 「結果可以繼續編輯；這裡檢查內容與版面。」 |
| 1:40–1:55 | 同任務個人化對照；或本次改英文 | 「相同資料依不同工作要求呈現。」覆寫規則應先修好驗收。 |
| 1:55–2:00 | 手機查看或成果全景 | 延伸功能點到即可。 |

影片等待段可剪輯／加速，畫面明示，實際耗時另外列出。保留未剪輯版供查驗。現場口說版不要疊加旁白；字幕只寫關鍵操作。展場循環版另加字幕，才能在無解說時成立。

不必把所有功能塞入影片。圖片、影片生成、Drive 等可放附錄或 10 秒成果拼圖，避免主軸被大量服務名稱淹沒。播放影片本身必須離線可用，另備 PDF 與靜態截圖。

## 8. 比賽與求職的作品包

同一專案準備不同入口：

- 專題展：十分鐘簡報、兩分鐘影片、可操作案例；讓陌生人迅速理解用途。
- 比賽：補目標使用者、比較基準、實驗结果、使用者回饋、限制與發展方向。未指定比賽，這不是特定評分規則。
- 軟體／AI 應用求職：README 五分鐘讀完、架構圖、三份設計決策記錄、一個可重現修復案例、測試與 CI、安裝步驟、發行版本。
- AI 研究職缺：還需更嚴謹的研究問題、基準與消融實驗；目前專案最直接展現的是應用工程能力，並不自動等同模型研究成果。

履歷可寫的現有版本：「開發 C#/.NET WPF AI 工作台，整合多模型路由、節點流程、偏好記憶與文件產出；抽離執行核心並建立自動化測試，目前 249 項通過。」

完成實驗後才加：「在固定 N 項任務與 M 位試用者中，……改善 X%，成本為……。」不要預填百分比。另附本人負責項目、第三方能力與 AI 協作方式，面試時能解釋設計與除錯過程。

## 9. 執行順序

1. 先處理重跑保留產物、預算語意、工作流匯流政策；統一個人化覆寫。
2. 固定一項展示任務，收集真實成品和完整執行紀錄。
3. 完成小型個人化對照與外部試用，保留原始資料和失敗結果。
4. 錄兩分鐘影片，再按十分鐘表製作簡報；已有結果才放結論圖。
5. 整理發布版本、README、架構與設計決策，形成能被別人驗證的作品集。

最重要的轉變：下一階段的進度應以「多證明了一件什麼事」衡量。可靠性修復、個人化有效性、使用者成功完成任務，都是能長期留下價值的證據。
